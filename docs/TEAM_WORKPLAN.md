更新：2026-11-06。這是可認領的分工建議，不代表已由任何具名組員承諾。使用者負責 Codex 開發與整合；其餘三人暫稱 A／B／C，由團隊自行認領。正式截止日與老師評分規準尚待確認，以下採相對工作日。

- 即時網頁搜尋、完整多語辨識、PTT／Dcard 覆蓋及排名品質評估仍未完成。TMDB 不會提供論壇文章。

## A 的執行步驟

1. 認領 Issue，先列候選 10 部；涵蓋至少三個製作國家，避免全是同一種題材。
2. 逐部確認是 TV 影集、真人劇情或迷你劇；記錄是否有同名翻拍。無法確認範圍則標「待確認」。
3. 找到 TMDB 的 TV 頁與 ID。專案本地 series ID 與 TMDB TV ID 是不同命名空間，不能直接互換。
4. 查核繁中、簡中、英文、日文、韓文別名。每個別名獨立附來源與查核日期；查不到就留空並記錄缺口，不使用機器翻譯當證據。
5. 先交兩部請開發者檢查格式，再完成其餘八部。由開發者驗證後匯入；不要編輯正在使用的 curated.sqlite，該資料庫目前要求與內建 catalog 完全相符。
6. 原創簡短導覽文字可以交付；不要貼整篇百科、影評、討論串或劇情文到 repo。

| 本地 ID（未匯入可留空） | TMDB TV ID | 原名 | 製作國家 | 真人劇情範圍證據 | 同名風險 | 狀態 |
|---|---|---|---|---|---|---|
| 待分配 | 待查 | 待查 | 待查 | 來源連結 | 待查 | 待查 |

別名逐筆記錄：

| TMDB TV ID | 語言／地區 | 別名原文 | 來源連結 | 查核日期 | 已核對／待確認 | 備註 |
|---|---|---|---|---|---|---|
| 待查 | zh-Hant／zh-Hans／en／ja／ko | 待查 | 待查 | YYYY-MM-DD | 待確認 | 不自行翻譯 |

驗收：10 部各有明確身分與來源；所有有填的別名都有證據；缺漏誠實標記。不是強制每部湊滿五種語言。

## B 的執行步驟

1. 先依目前分支的 runbook 啟動；在紀錄中寫分支／commit、日期、瀏覽器與螢幕尺寸，不共用 API 權杖。
2. 與 A 確認預期身分再跑查詢，分清「TMDB 資訊區」和「本地網頁結果」。
3. 建立下列 30 筆首輪案例；可依 A 查到的資料選查詢，不能捏造預期：
   - 五種語言名稱：10 筆。
   - 同名、翻拍或模糊名稱：4 筆。
   - 電影、動畫、實境等範圍外項目：4 筆。
   - 空白、特殊字元、大小寫／全半形：4 筆。
   - 分類切換、空分類恢復、快速連續查詢：4 筆。
   - 手機窄版、鍵盤操作、載入／錯誤狀態：4 筆。
4. 每筆標 PASS／FAIL／BLOCKED／NOT RUN。沒有資料、憑證或測試環境就標阻塞；不要為了湊通過率修改預期。
5. Bug Issue 附最短重現步驟、預期／實際結果、截圖、影響程度與版本；修正後由 B 重跑原案例。
6. API 故障、限流等情境優先用開發者提供的 mock 測試，不故意耗盡真實 API 配額。

|---|---|---|---|---|---|---|
| QA-01 | 待填 | 待填 | 待填 | 尚未執行 | NOT RUN | — |

驗收：30 筆都有明確預期與執行狀態；已執行的案例可重現；缺陷有追蹤。測試案例涵蓋五語不等於五語功能全部通過。

## C 的執行步驟

1. 向老師確認必要資料結構、Tree／BFS／HTML parsing／LLM 比較是否必做、個人貢獻及 AI 工具揭露要求、截止日、報告與展示形式。原文或課程文件附來源；未回覆標待確認。
2. 比較 2–3 個可申請的網頁搜尋服務，引用官方文件與查核日期；檢查是否仍開放新客戶。
3. 逐項確認結果顯示、混合來源、自訂重新排序、快取／持久保存、snippet、分頁、署名、配額及費用。網站公開不代表可以爬取。
4. PTT／Dcard 覆蓋未實測就標未知。服務獲團隊同意並設定憑證後，再執行 SOURCE_POLICY.md 的 20 筆有限測試；不繞過登入、403 或 CAPTCHA。
5. 列出比較結果交使用者決定；不新增訂閱、不開啟付費。團隊原訂 NT$300–1,000 是總預算規劃，不代表已核准支出。
6. 整理實際程式中的 HashMap、HashSet、ArrayList、PriorityQueue／倒排索引用途，與開發者核對後寫報告；尚未實作的功能分開列為規劃。

## GitHub 協作方式

- 每人先認領一個 Issue：目的、交付檔案、驗收條件、依賴、阻塞、狀態。實際 GitHub 帳號由團隊提供，不在本文件替人指派。
- 分支範例：data/series-research、test/search-acceptance、docs/provider-study；每次提交只含該任務。
- PR 說明：做了什麼、證據／來源、怎麼驗證、尚未完成什麼；一位其他組員審查後再合併。不要直接將不同工作混進 main。
- 現有功能 PR 有依賴順序；整合者先確認 base 分支及 CI，再合併，不只看最後一個 PR。
- 權杖只存在各自本機環境變數；不要貼聊天室、Issue、PR、截圖或提交資料庫。API 資料與文章不可因為「測試用途」就任意複製。
- 每週共同展示一次；每人說明自己的成果、失敗案例與下一步，確保都能解釋查詢→影集辨識→索引→去重→排名。
- 依老師規定揭露 Codex 使用；資料查核、測試、審查、設計及整合都據實記錄，不虛構個人程式貢獻。
